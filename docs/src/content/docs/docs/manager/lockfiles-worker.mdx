The lockfiles package contains the Cloudflare Worker used by `outfitting-manager`. It stores generated state that is not committed to Git, so it can be restored after rebuilding or replacing a machine.

KV holds content-addressed blobs; D1 holds searchable metadata. See [storage](/docs/manager/architecture#storage) for the storage model.

## Cloudflare setup

Install the monorepo dependencies and authenticate Wrangler:

```bash
bun install
cd manager/lockfiles
bunx wrangler login
```

Create the D1 database and KV namespace:

```bash
bunx wrangler d1 create outfitting-lockfiles --location=weur
bunx wrangler kv namespace create outfitting-lockfiles
```

Copy the returned D1 `database_id` and KV namespace `id` into `wrangler.jsonc`. The Worker uses the bindings `DB` and `LOCKFILES`; these are intentionally separate from the installer Worker's bindings.

Set the shared bearer token as a Worker secret:

```bash
bunx wrangler secret put OUTFITTING_LOCKFILES_TOKEN
```

Apply the schema and deploy:

```bash
bun run migrate:remote
bun run deploy
```

`wrangler deploy` prints the Worker URL. Configure it in the [manager CLI](/docs/manager/cli#configure-lockfile-storage).

For local Worker development, apply the migration locally before starting the development server:

```bash
bun run migrate:local
bun run dev
```

## HTTP API

Every request requires `Authorization: Bearer <OUTFITTING_LOCKFILES_TOKEN>`.

| Method   | Route                               | Result                                                |
| -------- | ----------------------------------- | ----------------------------------------------------- |
| `PUT`    | `/lockfiles/:machine/:kind`         | Stores/promotes the body and returns `{ hash, size }` |
| `GET`    | `/lockfiles/:machine/:kind`         | Returns the latest raw content as text                |
| `GET`    | `/lockfiles/:machine/:kind/history` | Returns `{ hash, size, created_at }[]`, newest first  |
| `GET`    | `/lockfiles/:machine`               | Returns a sorted JSON array of tracked kinds          |
| `DELETE` | `/lockfiles/:machine/:kind/:hash`   | Deletes one D1 row                                    |

`PUT` accepts an optional standard `If-Match: "<sha256>"` header. The D1 promotion and head update are atomic; a stale expected hash returns HTTP 412 without advancing the head. Deleting the current head returns HTTP 409.

## Homebrew inventories

Homebrew does not create or support lockfile. The macOS integration records a sorted, versioned inventory after successful Homebrew sync and upgrade operations while keeping the committed Brewfile as desired state.
