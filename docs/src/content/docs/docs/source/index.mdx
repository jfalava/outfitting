Outfitting reads declarations from a source root. A **local source** is an existing checkout used in place. A **remote source** is a profile-scoped snapshot materialized under the manager's state root. This sparse source pull is separate from [`sync pull`](/docs/cli/sync/), which downloads machine lockfiles.

## Source selection and state paths

`config.toml` selects exactly one source: a local `path`, or a remote `repository` and `ref`. The config file defaults to `<stateRoot>/config.toml`; the state root defaults to `~/.config/outfitting` on Unix and `%LOCALAPPDATA%/outfitting` on Windows. `OUTFITTING_STATE_ROOT` changes the state root, and `OUTFITTING_CONFIG` selects a different config file.

| Source | Resolution | Ownership and behavior |
| --- | --- | --- |
| Local `path` | Relative paths resolve from the directory containing `config.toml`. | The CLI validates and reads the existing checkout directly. It does not clone, copy, refresh, or delete it. Changes in that checkout are visible on the next command that reads it. |
| Remote `repository` + `ref` | The selected files are materialized at `<stateRoot>/source`. | The CLI owns this sparse snapshot and replaces it during an online refresh. |

`OUTFITTING_REPO` overrides the configured source with a local checkout for the current process. Commands that expose `--repo` provide the same kind of invocation-only override. Neither override changes `config.toml` or refreshes the managed remote snapshot.

`init` creates the state-root directory when needed, but it does not create a source checkout or write `config.toml`. [`config migrate`](/docs/cli/config/) writes TOML from supported legacy configuration. A local checkout must already exist and satisfy the selected profile's declarations.

## Files included in a sparse pull

The selected platform and profile determine the remote path closure. Declared directories contribute their files recursively; unrelated repository files are not copied. Additional `paths` declarations add files or directories to the selection.

| Platform | Selected remote files |
| --- | --- |
| Linux | Each declared apt and pacman manifest, the Nix flake directory when present, and additional declared paths. |
| macOS | The declared Nix flake directory and Darwin configuration, the optional Brewfile and fonts manifest, and additional declared paths. |
| Windows | Winget manifests for the selected profile set, plus any declared shared Scoop, PowerShell, fonts, or registry files. |

Each online pull resolves the configured ref to one immutable revision and reads the selected files from that revision. Public GitHub sources use the GitHub tree and file endpoints; other GitHub hosts use `gh api`; other Git remotes use a depth-one temporary checkout. Only regular files are supported in remote selections: selected symlinks and submodules are rejected. A local checkout can be used when those Git entries are required.

## Remote snapshot lifecycle

An online refresh computes the selected platform/profile declarations, fetches their files into a sibling staging directory, writes `.outfitting-source.json`, and validates the staged source. The metadata records the repository, ref, resolved revision, and a hash of the selected declarations. The CLI then renames the current snapshot to a temporary backup and publishes the validated staging directory as `<stateRoot>/source`.

| Event | Result |
| --- | --- |
| First successful online refresh | Creates `<stateRoot>/source` with only the selected files and metadata. |
| Successful refresh | Replaces the whole snapshot. Files no longer selected are removed when the previous directory is deleted. |
| Fetch or validation failure | Removes the staging directory and leaves the previously published snapshot unchanged. |
| Publish failure | Attempts to restore the previous snapshot. If restoration also fails, its backup path is reported and retained for recovery. |
| Successful publish cleanup | Removes the old backup. If backup cleanup itself fails, the new snapshot remains active and the backup may remain on disk. |

The temporary Git checkout used for non-GitHub remotes is removed after file copying. Staging directories are removed after failed refreshes. A local source is never part of this swap and is never deleted by it.

## Refresh and cache-only use

Local paths and `OUTFITTING_REPO` overrides bypass sparse pulls. For remote sources, command defaults are:

| Operation | Source behavior |
| --- | --- |
| `init` | Refreshes online by default on every platform. `--no-refresh` validates and reuses the current snapshot. |
| macOS or Linux `apply` | Refreshes online by default. `--no-refresh` uses the existing source. |
| Windows `apply` | Validates and reuses the existing snapshot; it does not refresh it. |
| macOS or Linux `nix` actions | Refresh online by default. `--no-refresh` validates and reuses the existing snapshot. |
| Linux `diff` | Uses the cache by default; `--refresh` fetches the selected source. `--offline` and `--refresh` cannot be combined. |
| `validate`, `status`, and `source path` | Validate or inspect the existing snapshot without fetching. |
| macOS or Windows `diff` | Uses the selected checkout or validates the existing remote snapshot without refreshing it. |

Offline validation requires metadata matching the current repository, ref, platform, and selected declarations, then validates the declared files. It cannot determine whether a moving remote ref has advanced since the last refresh. Changing the selected profile or its declarations can make a cache unusable offline.

Refreshing online materializes the new selection and replaces the old tree. Switching from a remote source to a local path does **not** remove `<stateRoot>/source`; the unused snapshot remains until a later successful remote refresh or manual deletion. There is no CLI cache-prune command. Deleting `<stateRoot>/source` manually clears only the managed snapshot; it does not delete a configured local checkout.
