`outfitting-manager` reads machine configuration only from BYOR. Choose either a local checkout with a root `outfitting.json`, or a remote Git repository and profile map stored locally as `byor.json`. The manager does not infer a repository, branch, profile, or file path.

## State root

The default state root is `~/.config/outfitting` on macOS and Linux, and `%LOCALAPPDATA%\outfitting` on Windows. Set `OUTFITTING_STATE_ROOT` to use another directory.

| Entry               | Purpose                                                              |
| ------------------- | -------------------------------------------------------------------- |
| `config.json`       | Machine ID and selected Linux profile.                               |
| `byor.json`         | Local remote repository, Git ref, and profile/path map.              |
| `source/`           | Validated managed snapshot of the selected remote BYOR files.        |
| `repo-path`         | Path to the selected local checkout or managed snapshot.             |
| `windows.lock.json` | Windows profile selection, package ownership, and operation history. |

`OUTFITTING_REPO` or an explicit `--repo <path>` selects a local checkout and takes precedence over the remote map. A local checkout must contain a valid root `outfitting.json`. Without a local checkout, commands require a configured `byor.json`; otherwise they stop with setup guidance before fetching or applying anything.

## BYOR configuration

### Local checkout: `outfitting.json`

Declare repository-relative files and arbitrary profile names at the repository root. For example:

```json
{
  "schema": 1,
  "profiles": {
    "debian-work": {
      "linux": {
        "apt": { "manifest": "ops/linux/debian.txt" }
      }
    },
    "workstation": {
      "macos": {
        "nix": {
          "flake": "hosts/mac",
          "attribute": "darwinConfigurations.workstation.system"
        },
        "brewfile": "ops/mac/Brewfile"
      }
    },
    "base": {
      "windows": {
        "winget": { "manifest": "ops/windows/base.txt" }
      }
    }
  }
}
```

Validate a checkout without fetching or changing machine state:

```bash
outfitting-manager validate --repo ~/src/machine-config --platform linux --profile debian-work
```

### Remote repository: `byor.json`

Run `outfitting-manager byor` to record a Git repository, ref, profile, and selected paths under the state root. This local map can describe a repository that does not contain `outfitting.json`; it does not modify the remote repository.

The remote can use GitHub, another Git host, HTTPS, or SSH. GitHub sources use commit-pinned reads. Other remotes use Git and the credentials configured for the current user. Select profiles and paths in the map; only their declared closure is fetched.

## Profiles and optional components

- **Linux and macOS:** Select one profile at a time. Linux commands require `--profile` for initialization and setup; later commands can use the saved profile where supported. macOS can omit `--profile` only when its source uniquely identifies a profile.
- **Windows:** Profiles can be composed with `--profile base,dev`. A contract may set `windows.defaultProfiles`; when omitted, all declared Windows profiles are selected. Shared Scoop, PowerShell, fonts, and registry components are skipped unless declared.
- **Paths:** Every declaration is relative to the repository root and must remain inside it. Nix flake directories are fetched as complete trees.

## Refresh and offline behavior

Remote refresh fetches the selected BYOR closure into a staging directory, validates it, and publishes it only after the complete source passes validation. A failed refresh leaves the prior published snapshot intact. Local checkouts are read directly and are never silently fetched from `origin/main`.

`--no-refresh` uses the existing validated source snapshot. Offline source use requires a previously validated snapshot for the configured repository and ref; it never falls back to raw URLs, loose manifests, or another cache. Package-manager offline behavior is separate and varies by platform.

## Migrating from raw routes or defaults

Remove raw manifest URL/ref and Windows route settings. Either add a root `outfitting.json` to your checkout or run `outfitting-manager byor` to declare the remote Git source and every needed path. Choose your own profile names, then run `init` or `setup` with the selected profile. There is no built-in profile, default repository, or legacy route fallback.

See the platform guides for [Linux](/docs/source-configuration/byor/linux/), [macOS](/docs/source-configuration/byor/macos/), and [Windows](/docs/source-configuration/byor/windows/), and the [`byor` command](/docs/cli/byor/).

## Machine ID

The machine ID resolves from `OUTFITTING_MACHINE_ID`, then `config.json` `machineId`, then the automatic `<username>:<architecture>-<platform>` value. For example, `jfalava:aarch64-darwin`. The ID scopes remote lock and inventory state.
