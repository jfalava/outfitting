Outfitting reads a single machine-local `config.toml`. By default it lives at `~/.config/outfitting/config.toml` on Linux and macOS, or `%LOCALAPPDATA%\outfitting\config.toml` on Windows. `OUTFITTING_STATE_ROOT` changes the state root. Global `--config <path>` or `OUTFITTING_CONFIG` selects another config file; a relative `[source].path` resolves relative to that config file, not the current working directory. Command arguments override environment variables, which override TOML values where an override is supported.

```toml
schema = 1
machine_id = "workstation"

[source]
path = "../machine-config"

[linux]
profile = "debian-work"

[macos]
profile = "workstation"

[windows]
profiles = ["base", "dev"]

[windows.shared.scoop]
manifest = "ops/windows/scoop.txt"

[windows.shared.powershell]
path = "shell/Microsoft.PowerShell_profile.ps1"

[windows.shared.fonts]
manifest = "ops/windows/fonts.txt"

[windows.shared.registry]
path = "ops/windows/registry.reg"

[profiles.debian-work.linux.apt]
manifest = "ops/linux/debian.txt"

[profiles.workstation.macos]
brewfile = "ops/mac/Brewfile"

[profiles.workstation.macos.nix]
flake = "hosts/mac"
attribute = "darwinConfigurations.workstation.system"
darwin = "hosts/mac/darwin.nix"

[profiles.base.windows.winget]
manifest = "ops/windows/base.txt"

[profiles.dev.windows.winget]
manifest = "ops/windows/dev.txt"
```

Choose **either** local `path` **or** remote `repository` and `ref` in `[source]` (for example `repository = "git@code.example.com:team/machine-config.git"` and `ref = "main"`). Declaration paths are relative to the source root and must stay inside it. Linux supports `apt.manifest`, `pacman.manifest`, `nix.flake`/`nix.attribute`, and `paths`; macOS supports `nix.flake`/`nix.attribute`/`nix.darwin`, `brewfile`, `fonts.manifest`, and `paths`. Windows profiles declare `winget.manifest`; optional `[windows.shared]` supports `scoop.manifest`, `powershell.path`, `fonts.manifest`, and `registry.path`. Linux and macOS select one profile; Windows composes the names in `profiles`.

## Runtime state and migration

Remote refresh stages and validates selected declarations before publishing the `source/` runtime cache under the state root. A failed refresh keeps the previous validated snapshot; offline use requires an existing snapshot. Local sources are read directly, not fetched from their Git remote. Lock files and operation history remain runtime state outside the source checkout. `outfitting-manager source path` prints the resolved source path in a machine-readable form for scripts.

For first use of a remote source, create a local `config.toml` containing its repository, ref, and profile declarations before running `init`. The `--repo` flag and `OUTFITTING_REPO` environment variable override only a local checkout path; they do not accept a remote URL or ref.

Normal commands do **not** read legacy `config.json`, `byor.json`, `repo-path`, or repository `outfitting.json`. To convert old local configuration once, run `outfitting-manager config migrate`, then inspect the generated TOML before applying changes. Do not use the retired `byor` command.

See the platform examples for [Linux](/docs/source-configuration/byor/linux/), [macOS](/docs/source-configuration/byor/macos/), and [Windows](/docs/source-configuration/byor/windows/).

## Machine ID

Set optional `machine_id` in TOML, or override it with `OUTFITTING_MACHINE_ID`. Otherwise Outfitting derives an ID from the username, architecture, and platform. It scopes remote lock and inventory state.
