Outfitting keeps machine-local state separate from the repository source it consumes. The state root contains configuration, cached declarations, and the managed source used by later commands.

## State root

The default state root is:

| Platform        | State root                         |
| --------------- | ---------------------------------- |
| macOS and Linux | `~/.config/outfitting`             |
| Windows         | `%USERPROFILE%\.config\outfitting` |

Set `OUTFITTING_STATE_ROOT` to use another location. The important entries below live under that root:

| Entry         | Purpose                                                                             |
| ------------- | ----------------------------------------------------------------------------------- |
| `config.json` | Manifest source, machine ID override, Windows routes, and the active Linux profile. |
| `manifests/`  | Materialized copies of fetched package lists and other declarations.                |
| `source/`     | Managed sparse source for macOS and Linux when no full checkout is selected.        |
| `repo-path`   | Saved path to the source selected with `--repo` or to the managed sparse source.    |

For macOS and Linux, `OUTFITTING_REPO` takes precedence over the saved `repo-path`. When neither is configured, setup uses the managed sparse source for the selected platform or profile. Windows reads cached manifests from the configured manifest source, or from a local BYOR checkout when `outfitting.json` declares Windows profiles.

## Profiles

| Platform | Profile model                                      | Typical selection                                                 |
| -------- | -------------------------------------------------- | ----------------------------------------------------------------- |
| macOS    | One exclusive profile (built-in layout or BYOR)    | Optional `--profile` when a BYOR contract declares several names. |
| Windows  | Multiple comma-composable bundles                  | `--profile base,dev`                                              |
| Linux    | One exclusive profile (built-in or BYOR)           | `--profile generic-linux`, `--profile ubuntu-wsl`, or a BYOR name |

Windows profiles are comma-composable. Linux and macOS profiles are exclusive: selecting one replaces the active profile rather than composing with it.

Windows commands and Linux `apply` reuse the saved active selection when `--profile` is omitted. New Windows state uses configured default profiles (or BYOR `windows.defaultProfiles`); new Linux state defaults to `generic-linux`. Linux `init` and `setup` default explicitly to `generic-linux`, so pass `--profile` when preparing a different Linux profile. Package upgrades do not select a profile; Linux Nix actions use the saved profile.

## BYOR (`outfitting.json`)

Bring Your Own Repo (BYOR) lets you manage your systems using your own repository structure instead of Outfitting's built-in layout.

Place an `outfitting.json` file at the root of your local repository. A single configuration (using schema `1`) can define profiles for `linux`, `windows`, and `macos`.

Before applying changes, verify your setup without touching system state:

```bash
outfitting-manager validate --repo ~/src/my-machine-config --platform linux
```

Pass `--platform` whenever `outfitting.json` defines profiles for multiple platforms. A local checkout (via `--repo`, `OUTFITTING_REPO`, or saved `repo-path`) is read directly and may contain `outfitting.json`.

A remote GitHub repository does not need an Outfitting file. Run `outfitting-manager byor` to write `~/.config/outfitting/byor.json` from your answers, then `init` without `--repo`. Public `github.com` uses raw URLs. Any other GitHub host, including `*.ghe.com`, uses `gh api` against that hostname. Authenticate first with `gh auth login --hostname <host>`. The local map names the files that are fetched. A flake directory is fetched as a tree. The wizard requires an explicit list of files outside that directory, or an explicit empty list. A missing mapped file leaves the previous tree in place. Refresh reads the local map and does not rewrite it.

| Platform | Profile configuration                    | Guide                                               |
| -------- | ---------------------------------------- | --------------------------------------------------- |
| Linux    | `profiles.*.linux` (apt / pacman / nix)  | [BYOR for Linux](/docs/source-configuration/byor/linux/)     |
| Windows  | `profiles.*.windows.winget` + optional top-level `windows` | [BYOR for Windows](/docs/source-configuration/byor/windows/) |
| macOS    | `profiles.*.macos` (nix + optional brewfile/fonts/paths) | [BYOR for macOS](/docs/source-configuration/byor/macos/)     |

See also the [`validate`](/docs/cli/validate/) command reference.

## Machine ID

The machine ID resolves from `OUTFITTING_MACHINE_ID`, then `config.json` `machineId`, then the automatic `<username>:<architecture>-<platform>` value. For example, `jfalava:aarch64-darwin`. The username resolves from `USER`, then `USERNAME`, then the operating-system account. Supported CPU names normalize to `aarch64`, `x86_64`, or `i686`.

The ID scopes remote state. Set it deliberately when multiple installations should share an identity; otherwise let Outfitting derive it.

## Platform source layouts

Each platform consumes a different local source layout. macOS and Linux fetch only the files required by their selected source bundle when no full checkout is selected. Windows caches the repository-relative manifests and profile files it needs.

### Windows

Windows can use traditional `config.json` routes or a repository-owned `outfitting.json` file. See [BYOR for Windows](/docs/source-configuration/byor/windows/).

Windows stores configuration and fetched manifests under:

```text
%USERPROFILE%\.config\outfitting
```

`config.json` records the manifest source and repository-relative Windows routes. `manifests` contains the selected WinGet files, the configured Scoop manifest, and the cached PowerShell profile. When using hosted routes, Windows does not require a full repository checkout. When using BYOR, Outfitting reads manifests directly from your local repository.

The installer links these PowerShell profile entry points to the cached profile:

```text
%USERPROFILE%\Documents\PowerShell\Microsoft.PowerShell_profile.ps1
%USERPROFILE%\Documents\PowerShell\Microsoft.VSCode_profile.ps1
%USERPROFILE%\Documents\WindowsPowerShell\Microsoft.PowerShell_profile.ps1
    -> %USERPROFILE%\.config\outfitting\manifests\<configured PowerShell route>
```

Existing profiles are backed up with a timestamp before they are replaced. Windows symbolic links require Developer Mode or an elevated installer session.

### macOS

```text
~/.config/outfitting/repo-path -> ~/.config/outfitting/source
~/.config/home-manager -> ~/.config/outfitting/source/system/macos
~/.nixpkgs/darwin-configuration.nix -> ~/.config/outfitting/source/system/macos/darwin.nix
```

Without a local BYOR configuration, the macOS manager fetches only Outfitting's required paths into `~/.config/outfitting/source` without cloning the entire repository or creating a repository `flake.lock`. `outfitting-manager init` validates this sparse source before `outfitting-manager setup` applies it. With a local `outfitting.json` macOS profile, flake and Brewfile paths are resolved directly from your repository. See [BYOR for macOS](/docs/source-configuration/byor/macos/).

### Linux

Linux keeps a profile-scoped sparse source at:

```text
~/.config/outfitting/source
```

For built-in profiles, the bundle contains the selected profile's package manifest and, for Nix-backed profiles, the shared modules, dotfiles, flake, lockfile, bootstrap, and Zsh plugin.

Home Manager links for built-in Nix-backed profiles point to the selected source:

```text
~/.config/home-manager -> ~/.config/outfitting/source/system/ubuntu-wsl
~/.config/home-manager -> ~/.config/outfitting/source/system/oci-agents
```

Use [BYOR for Linux](/docs/source-configuration/byor/linux/) if you want Outfitting to read directly from your own repository checkout and `outfitting.json` configuration instead of the default sparse source.
